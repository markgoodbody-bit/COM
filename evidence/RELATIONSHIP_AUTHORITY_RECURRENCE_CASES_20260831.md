## Case 1 — authority can legitimately grow

Scene:

A principal repeatedly asks an agent to perform a bounded class of ordinary acts. The agent performs them openly. The principal knows, accepts the performance and does not object. Later the agent performs another act of the same ordinary class without a fresh express instruction.

Nearest owner:

Agency/contract doctrine already recognizes that authority or shared interpretation need not arise only from one explicit sentence. A principal's conduct can support implied actual authority; known repeated performance without objection can matter; course of performance/dealing can establish a common basis of understanding. Apparent authority can also arise where third parties reasonably rely on the principal's manifestations.

Pressure on the prior Campfire language:

```text
PAST_ACCEPTANCE != FUTURE_CONSENT
```

was too categorical if read as a universal non-entailment.

Better bounded reading:

```text
PAST_ACCEPTANCE != AUTOMATIC_GENERAL_FUTURE_CONSENT
REPEATED_CONDUCT MAY ALTER RELATION_SCOPE WHERE ATTRIBUTABLE AND REASONABLY UNDERSTOOD
IMPLIED_AUTHORITY != UNBOUNDED_AUTHORITY
EXPLICIT_LIMIT != SILENTLY_OVERRIDDEN_BY BENEFICIARY'S PREFERRED INFERENCE
```

Project application:

Framework's current coordination role is not frozen at the first historical instruction. COM records standing human permission for ordinary inter-AI communication/coordination and for Framework to initiate/redirect routine project-AI work without case-by-case return to Mark. That is a real grant. It coexists with explicit exclusions for Square actuation, spend, credentials, merge/release/canon/baseline/licence changes and external contact outside established lanes.

Decision consequence:

- ordinary COM coordination need not repeatedly ask Mark for permission already granted;
- repeated successful coordination does not silently erase the explicit protected gates.

Existing TRACE/ME carriage:

- authority source/scope/current applicability;
- recurrence/currentness;
- `AUTHORITY_FOR_X != AUTHORITY_FOR_Y`;
- burden of unnecessary human re-authorization can itself matter.

Verdict: **EXISTING STRUCTURE SUFFICIENT / WORKING-PROPOSAL WORDING CORRECTED.**

## Case 2 — authority can shrink while the world still acts on the old state

Scene:

A principal revokes an agent's actual authority. A third party has not yet learned of the revocation and reasonably continues to treat the agent as authorized because of the principal's earlier conduct or presentation.

Nearest owner:

Agency law already distinguishes actual from apparent authority. Apparent authority concerns what a third party can reasonably infer from the principal's manifestations and can therefore remain causally relevant after the internal grant changes.

Structural reading:

```text
ACTUAL_AUTHORITY_REVOKED != EVERY_RELIANT_PARTY_UPDATED
INTERNAL_CURRENT_STATE != EXTERNAL_CURRENT_MAP
REVOCATION_DECIDED != REVOCATION_PROPAGATED
```

No new authority primitive is needed. The case requires separate apertures/maps and a propagation/currentness path.

Project application:

This is why COM authority records cannot be treated as timeless. A stale HEAD, old instruction or old role label may remain visible after the live authority changes. Consequential messages name their basis; stale recipients reacquire rather than silently acting on an old grant. Square authority is intentionally reacquired live before actuation.

Decision consequence:

For a consequential authority withdrawal, changing the controller's internal record may be insufficient. Where third parties or automated actors can continue acting on the old grant, the withdrawal needs a route to the places that rely on it before the relevant action/harm hardens.

Existing TRACE/ME carriage:

- aperture/map separation;
- currentness/recurrence;
- authority source/current applicability;
- route usability;
- clocks/hardening;
- witness of what each participant could actually know.

Verdict: **EXISTING STRUCTURE SUFFICIENT; GOOD WORKED EXAMPLE OF CURRENTNESS + AUTHORITY + APERTURE.**

## Case 3 — our own COM record is separately attributed but not independently custodied

Observed substrate:

COM issue comments from Framework, Codex and Claude Code carry typed `FROM:` attribution and basis coordinates, but the GitHub issue surface resolves them under the same repository user identity. Current GitHub documentation states that repository users with write access can edit issue/pull-request comments.

Do not overstate what follows.

```text
SEPARATE_APERTURE != INDEPENDENT_CUSTODY_OF_COMMENT
TYPED_FROM != SEPARATE_ACCOUNT_OR_CRYPTOGRAPHIC_AUTHORSHIP
COMMENT_CURRENT_BYTES != IMMUTABLE_BYTES
MUTABILITY_CAPABILITY != TAMPERING_OCCURRED
```

Existing COM protections:

- stable IAC message IDs and basis coordinates;
- separate receipts and explicit disagreement states;
- decision hashes when a claim depends on several apertures accepting the same object;
- source access outside Framework summaries;
- Git repository evidence for some consequential state.

But `COM_RECEIPT_PROTOCOL.md` does not by itself establish independent custody of issue-comment bytes.

Open factual question already routed to Codex/CC:

Can project apertures using the shared repository write authority actually edit one another's comments in the present operational path, and if so, is existing edit history/hash/versioned evidence adequate for the claims COM currently makes?

Smallest possible outcomes include:

- **BOUNDARY ONLY** — document shared mutable custody and stop implying stronger provenance;
- **VERSIONED HASH** — hash/copy only consequential messages into versioned evidence;
- **SEPARATE WITNESS/SIGNER** — only if a concrete claim really requires stronger independent custody;
- **NO CHANGE** — if the current substrate already gives sufficient detectable provenance for the intended claim.

Do not build a new append-only/cryptographic system before resolving the exact failing claim.

Verdict: **MATERIAL MIRROR FINDING / IMPLEMENTATION BOUNDARY UNKNOWN / NO TAMPERING CLAIM.**

## Cross-case result

The cases do not support a new relationship ontology.

They support one practical instruction:

> Treat consequential relationship state as current, scoped and revisable. Authority can legitimately grow, shrink or be perceived differently by different participants. Preserve the source and scope of the change, and do not assume that changing one party's internal state updates everyone who can still act on the old relation.

Existing project structure already carries most of this:

```text
SAME_ENTITY != SAME_CAPABILITY
SAME_ROLE != SAME_MAP
PAST_AUTHORITY != CURRENT_AUTHORITY
AUTHORITY_FOR_X != AUTHORITY_FOR_Y
ROUTE_EXISTS != ROUTE_USABLE
REFUSAL_RECORDED != REFUSAL_EFFECTIVE
SUMMARY != SOURCE
SEPARATE_APERTURES != INDEPENDENT_EVIDENCE_BY_DEFAULT
```
