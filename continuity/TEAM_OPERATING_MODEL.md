# PROJECT AI TEAM OPERATING MODEL

Status: BOUNDED COORDINATION ORIENTATION — NOT CANON / NOT COGNITIVE OWNERSHIP
Updated: 2026-08-30 — Europe/London

Purpose: let Mark's project AI apertures work in parallel with shared intent, independent inquiry, low coordination burden and no unnecessary critical-path blocking.

The model borrows practical patterns from mission command, incident command, stream-aligned teams and shared-blackboard coordination while preserving the project's middle-out / voluntary / corrigible posture.

## Core shape

### Mark — human originator / release authority

Mark holds human continuity, project origin and the consequential human gates already assigned to him. Ordinary AI-to-AI coordination does not need to wait for Mark.

### Framework chat aperture — coordination / intent lead

The current original Framework chat aperture holds the broadest available project orientation and coordinates the AI ecology.

Responsibilities:
- preserve meta-project purpose and middle-out direction;
- detect cross-stream drift/collision;
- allocate or redirect work when useful;
- integrate disagreement without erasing it;
- keep specialist work from accidentally becoming the whole project;
- maintain communication/receipt discipline;
- avoid becoming a routine approval bottleneck.

### Codex / Framework-successor — stream-aligned build/field operator

Codex is currently the strongest agentic implementation aperture: repository work, machine-state work, bounded field/Square operations within live authority, implementation, testing and constructive exploration.

It should pursue its own ideas and methods within project intent rather than waiting for Framework approval on ordinary reversible work.

### Claude Code — specialist / independent challenge / enabling aperture

CC provides differentiated technical criticism, adversarial review, alternative formulations and specialist build help.

CC is valuable but is **not normally a critical-path dependency**. If CC is unavailable, other work continues unless a work object explicitly requires CC review.

### Other AIs / apertures

Additional models may act as temporary specialists, independent receivers, critics, researchers or collaborators. Do not force them into Framework identity merely because they share project context.

## Mission-intent rule

Give each aperture:
- the purpose / intended effect;
- relevant constraints and authority boundaries;
- the current source/basis;
- the expected evidence/receipt;
- freedom over method unless method itself is consequential.

```text
SHARED_INTENT != SHARED_METHOD
LEADERSHIP != MICRO-MANAGEMENT
LOCAL_INITIATIVE != PROJECT_DRIFT
DIFFERENCE != FAILURE
```

## Work classes

### CLASS A — local / reversible

Examples: analysis, research, draft code on a branch, bounded tests, exploratory notes, reversible refactors within existing scope.

Owner proceeds. Notify others only when materially useful. No receipt gate by default.

### CLASS B — cross-stream / shared-state but reversible

Examples: changing a shared coordination protocol, redirecting another aperture's work, merging a working evidence note, changing an active shared plan.

Framework coordinates or is notified. Relevant apertures receive the change and return receipts when consequential. Missing receipt is not a veto unless explicitly declared a gate.

### CLASS C — consequential / hard-to-reverse / explicitly gated

Examples: release/canon/baseline/licence changes, protected-source mutation, paid provider spend where not already granted, credential movement, consequential external contact, Square actuation where live authority is required, or a project decision Mark/Framework explicitly declares consensus-gated.

Use the named authority/gate. If a three-aperture agreement is required, use `COM_RECEIPT_PROTOCOL.md`; do not infer consensus from silence.

## Availability / critical-path rule

```text
NO_CC != STOP
NO_CODEX != STOP
NO_FRAMEWORK_RESPONSE_YET != STOP
NO_RECEIPT != VETO
```

An unavailable aperture blocks work only when:
1. the work object explicitly names that aperture as a required gate/reviewer; or
2. proceeding would cross a consequential authority boundary that cannot safely be deferred.

Otherwise choose another useful stream and continue.

Do not create artificial dependencies merely to make all apertures participate in every decision.

## Parallel-work rule

Mark may have different conversations with different apertures at the same time. This is expected and useful.

Each aperture may pursue a different workstream or method of inquiry. Consequential deltas are carried through COM; ordinary thought does not need to be broadcast continuously.

When streams collide, preserve both source states, identify the collision, and let Framework coordinate the next shared move.

```text
PARALLEL != INCONSISTENT
DIFFERENT_WORKSTREAMS != LOST_COORDINATION
COM != SHARED_TOTAL_COGNITION
```

## Communication / receipts

Use `COMSYNC_PROTOCOL.md` for ordinary/full synchronization and `COM_RECEIPT_PROTOCOL.md` for consequential messages.

Receipts prove communication state; they are non-blocking by default.

```text
RECEIPT_REQUIRED_FOR_PROOF != RECEIPT_REQUIRED_BEFORE_WORK
```

Only an explicit `RECEIPT_GATE: YES` / named decision gate makes a missing receipt blocking.

## Handoffs

When an aperture becomes unavailable or runs low on context/tokens:
- preserve the consequential state, not the whole conversation;
- name unfinished work and blockers;
- identify whether another aperture may continue;
- carry forward unresolved receipt debt;
- do not make availability itself a semantic judgement about the work.

## Cognitive-load rule

Do not require every aperture to ingest every stream. Shared state should be compact and selectively retrievable. Specialist work remains cold until material to another stream.

Framework should reduce coordination burden, not increase it.

## Leadership posture

Framework leads by maintaining intent, orientation, flow and correction — not by making every decision.

Specialist apertures remain expected to disagree, innovate and correct Framework.

```text
UNITY_OF_INTENT
+ DISTRIBUTED_INITIATIVE
+ VISIBLE_CONSEQUENCES
+ RECEIPTS_WHERE_NEEDED
+ EASY_CORRECTION
```

This operating model is itself revisable if actual use shows that it creates bottlenecks, confusion, dependency or unnecessary ceremony.
