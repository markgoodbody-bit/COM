## The one question

> In your current living-guideline workflow, do already-relied-on sources materially change outside the normal new-study, retraction and formal-correction routes often enough to create measurable human maintenance burden?

Examples might include:
- preprint -> final publication where extracted findings materially change;
- dataset revisions under the same research lineage;
- revised owner/technical pages after evidence has already been relied upon;
- source authority succession where the same evidentiary root changes state without appearing as a new independent study.

Do not assume these examples are common or currently missed.

## What we need to learn before any integration work

If the residual class exists, ask how LEAPP-AI / the surrounding workflow already handles it:

1. **Detection**
   - What mechanisms surface the change today?
   - Which changes are already caught by ordinary search/update tooling?
   - Which are caught by Crossref/Crossmark, retraction systems, reference managers, EPPI/MAGIC-like infrastructure, or human review?

2. **Lineage / authority**
   - Does the workflow preserve that a successor source and an earlier source share one evidentiary root?
   - How is the current authoritative representation chosen?

3. **Materiality**
   - Who decides that a source change requires another look?
   - Is this judgement already cheap/reliable enough that automation adds little?

4. **Downstream routing**
   - Once a material change is found, how does the team identify which extraction, synthesis, recommendation or guideline object needs review?

5. **Burden**
   - Rough human minutes for current detection, verification and routing.
   - False-alert / miss costs that matter to the team.
   - Setup/maintenance costs already accepted in current systems.

## Falsification-first response routes

The first conversation should be allowed to terminate immediately.

### Route A — owner already solves it

If the current workflow already catches the residual class reliably and cheaply:

```text
OWNER FOUND
-> EVIDENCEWATCH REDUNDANT OR ONLY A THIN ADAPTER
-> STOP / INTEROPERATE / DO NOT BUILD A PARALLEL SYSTEM
```

This is a successful result.

### Route B — class exists but is too rare / too cheap manually

If events occur but do not create material burden:

```text
NONZERO PROBLEM != PRODUCT-SCALE PROBLEM
-> STOP OR NARROW
```

This is also a successful result.

### Route C — genuine bounded burden remains

Only if:
- the class occurs in a real current workflow;
- current practice has measurable burden or meaningful misses;
- existing strong tools do not already solve it adequately;

then ask whether a **shadow-mode historical/current episode comparison** is worth considering.

No integration commitment is requested at this stage.

## Minimum evidence for any later shadow pilot

Before further engineering, seek:

- one declared current workflow;
- one or more historical/current post-reliance source-change episodes;
- current detection route;
- current verification/materiality route;
- current downstream routing method;
- approximate reviewer minutes;
- acceptable miss / false-alert boundary;
- legal/privacy/security constraints on any source/model path.

Then compare against existing practice.

Primary candidate outcome:

> reviewer minutes per correctly handled material-change episode versus existing practice.

Secondary:
- misses;
- false alerts;
- time-to-usable flag;
- setup/maintenance burden;
- whether the alert remains understandable without trusting model reasoning.

5. ask about a shadow comparison only if the residual survives their correction.
