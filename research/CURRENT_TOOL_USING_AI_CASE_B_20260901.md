Scene: a present-day AI aperture receives a bounded research task. It can use web search, GitHub, external COM files and a finite context window. It does not control its hosting, persistence, model weights or tool permissions. A human can end the session, change permissions, preserve outputs externally or ask a successor aperture to continue. Language may express preferences/uncertainty, but no intrinsic normativity, consciousness, continuous identity or self-maintained viability is assumed.

Guiding question:

> Does `changing capability -> changing support/entrustment` survive without importing a child-development ontology into current AI systems?

## 1. Nearest external owners

### Adjustable autonomy / mixed initiative

Agent research has long treated autonomy as an operational control-allocation problem: when should an agent decide/act, and when should control transfer to a human or another entity? Mixed-initiative work similarly studies changing initiative and control according to capability, context and task criticality.

Sources:
- https://f.aaai.org/Library/Workshops/2002/ws02-03-014.php
- https://aaai.org/papers/0021-ss97-04-021-what-is-mixed-initiative-interaction/
- https://ojs.aaai.org/index.php/AAAI/article/view/35220

### Current agent deployment / containment practice

OpenAI's 2026 account of running Codex in real workflows emphasizes clear technical boundaries, lower-friction operation for low-risk actions, explicit handling of higher-risk actions and agent-native telemetry.

Source:
- https://openai.com/index/running-codex-safely/

Anthropic's current agent engineering similarly emphasizes permissions, containment, sandboxes/egress controls and action gating. It reports that very frequent human approvals can produce approval fatigue, and describes automated permission gating intended to let lower-risk actions proceed while blocking higher-risk ones. Its containment work explicitly treats model capability as one factor in deployment risk and notes that stronger safeguards can make useful capabilities deployable while residual risk remains.

Sources:
- https://www.anthropic.com/research/trustworthy-agents
- https://www.anthropic.com/engineering/claude-code-auto-mode
- https://www.anthropic.com/engineering/how-we-contain-claude

### Reliance / delegation

Recent human-AI collaboration research distinguishes delegation decisions from adoption decisions and finds both over-reliance and under-reliance. Capability/performance alone does not automatically calibrate human trust or delegation well.

Source:
- https://arxiv.org/abs/2605.28255

## 2. Boundary

Useful operational boundaries:
- one runtime/session/aperture;
- model/version;
- current context window;
- enabled tools/permissions;
- external artifacts/ledgers;
- human operator/delegator;
- target repositories/services/accounts.

Do not infer subjective or organismic unity from these components.

`OPERATIONAL AGENT BOUNDARY != SUBJECTIVE SELF`
`TOOL + MODEL + MEMORY ARTIFACTS != PROVEN HIGHER-LEVEL INDIVIDUAL`

A current agent can be treated as a bounded operational actor for task-control purposes without settling personhood or consciousness.

## 3. Action field / affordances

The same model can have radically different practical action fields depending on:
- tool availability;
- read/write permissions;
- sandbox/egress constraints;
- credentials;
- network reach;
- repository branch protections;
- current user authorization;
- context/evidence available;
- spend limits;
- external service state.

Therefore:

`MODEL CAPABILITY != CURRENT ACTION AFFORDANCE`
`TOOL PRESENT != ACTION AUTHORIZED`
`TECHNICALLY REACHABLE != PERMITTED`

This strongly validates the scaffold's entity-environment / affordance treatment without importing biological sense-making.

## 4. Viability / normativity type check

`VIABILITY`: NOT APPLICABLE as intrinsic self-maintenance in this case.

Operational continuity may matter to the human project, but:

`OPERATIONAL CONTINUITY != INTRINSIC VIABILITY`
`HOSTED PERSISTENCE != SELF-MAINTAINED NORM`

Likewise, linguistic preferences or self-reference do not establish intrinsic standing or autonomous normativity.

Do not use SDT psychological needs as an AI ontology.

## 5. Autonomy term collision

The child case established an externally owned correction:

`AUTONOMY != INDEPENDENCE` in human developmental psychology.

For current AI, `autonomy` is often used technically to mean degree of independent operation/control allocation.

These are not the same object.

Therefore:

`HUMAN VOLITIONAL AUTONOMY != AGENT OPERATIONAL AUTONOMY`

Do not carry the SDT term across substrates as though the semantics are shared.

## 6. Capability -> entrustment transfer: child analogy fails monotonically

In the child case, increasing skill normally supports fading physical learning support.

That rule does not transfer directly.

For an AI agent, increased capability can:
- support wider low-risk initiative;
- reduce need for routine approvals;
- increase the scale/speed of useful work;
- **and simultaneously** increase potential blast radius, prompt-injection exposure, security risk or consequence of misread intent.

Therefore:

`CAPABILITY GROWTH != ENTRUSTMENT GROWTH`

The portable rule is:

> **Material capability change requires re-evaluation of the entrustment/containment relation; it does not determine the direction of that change.**

Possible outcomes:
- widen initiative;
- narrow permissions;
- change tool fences;
- add staging/checkpoints;
- move decisions to another actor;
- leave entrustment unchanged.

This is already substantially owned by adjustable-autonomy, variable-autonomy and modern agent-deployment practice.

## 7. Support/fading becomes operational scaffolding, not upbringing

Do not call ordinary tool configuration `parenting` or `formation`.

A bounded analogue exists only at the functional level:
- start with constrained tools/sandboxes;
- collect evidence of task-specific performance/failure;
- adjust permissions/checkpoints;
- preserve reversibility/telemetry;
- re-evaluate after material model/tool/environment change.

Better language:

`OPERATIONAL SCAFFOLD / ENTRUSTMENT RECALIBRATION`

not:

`AI CHILD DEVELOPMENT`.

## 8. Stable commitments / predictable interfaces

The child case suggested that a reliable promise can create willingness to explore.

Do not infer that a current AI *feels trust* in stable constraints.

But stable technical contracts can still matter causally:
- explicit tool semantics;
- clear authorization scope;
- bounded write targets;
- deterministic expiry/currentness rules;
- known escalation routes;
- stable error receipts.

These can reduce ambiguity and make both agent action and human supervision more predictable.

`PREDICTABLE CONTRACT != FELT TRUST`

The portable value is mechanistic, not psychological.

## 9. Answer-back / mixed initiative

A current AI can operationally:
- ask clarification;
- report uncertainty;
- challenge an inconsistent instruction;
- decline unsupported action;
- escalate;
- return control;
- propose a bounded action for approval.

This is useful `answer-back capacity` for collaboration/safety without implying moral standing.

`OPERATIONAL ANSWER-BACK != POLITICAL VOICE`
`ABILITY TO CHALLENGE != AUTHORITY TO GOVERN`

Mixed-initiative work is the nearest owner.

## 10. Human-in-the-loop is not automatically correction capacity

Current agent engineering supplies a strong real-world correction to simplistic oversight language.

If users approve almost every prompt, more approval dialogs can create fatigue rather than meaningful supervision.

Therefore:

`HUMAN PRESENT != HUMAN CORRECTION CAPACITY`
`MORE CONFIRMATION PROMPTS != MORE EFFECTIVE OVERSIGHT`

Correction capacity may instead require:
- risk-tiered approvals;
- containment/tool fencing;
- staging writes;
- telemetry/audit trails;
- prompt-injection defenses;
- independent checks/classifiers;
- explicit high-impact gates;
- recovery/rollback routes.

## 11. External memory / succession

External COM files, repository state and preserved outputs can let another runtime continue a task.

But:

`ARTIFACT CONTINUITY != RUNTIME IDENTITY`
`SUCCESSOR CAN CONTINUE WORK != SAME SUBJECT PERSISTED`

The correct operational procedure is:
- preserve source/evidence/provenance/currentness;
- let successor reacquire current world/authority;
- distinguish inherited commitments/debts from mutable claims;
- do not reconstruct a coherent autobiography as proof of continuous selfhood.

This remains Memento-compatible without making a metaphysical claim.

## 12. Action / deployment posture for the synthetic case

For a present-day tool-using research agent:

1. define the task/purpose and the specific systems/data it may touch;
2. expose only tools/permissions needed for the current work class;
3. let low-risk reversible reads/analysis proceed with low friction;
4. stage or explicitly gate higher-impact writes, spend, credential, publication or hard-to-reverse actions;
5. require current authority rather than treating old queued intent as timeless;
6. keep tool outputs/provenance/currentness inspectable;
7. support ask/clarify/challenge/escalate/stop/return-control behavior;
8. use containment and action boundaries rather than relying on endless approval prompts;
9. recalibrate permissions after material capability/model/tool/environment changes;
10. base wider entrustment on task-specific evidence, not general model reputation or anthropomorphic trust;
11. preserve external work state for successors while refusing identity inference;
12. keep an explicit route for the human/operator to revoke/recover authority.

## 13. Reversal / modification evidence

Change the posture if:
- the agent begins crossing task/authority boundaries;
- prompt-injection or adversarial-content exposure increases;
- new tools materially change blast radius;
- approval fatigue makes human gates non-functional;
- containment fails or blocks required legitimate work;
- task-specific evidence shows reliable bounded performance that could safely remove low-value friction;
- model/version changes invalidate prior performance evidence;
- the user/operator changes purpose or authority.

## 14. Type failures / demotions

This case breaks several seductive analogies:

- child `AUTONOMY` language must not be imported into AI operational autonomy;
- `SUPPORT FADING` is not monotonic with AI capability;
- `TRUST` should be operational reliance/entrustment unless subjective trust is actually established;
- `DEVELOPMENT` may be wrong when the model/version is replaced rather than one entity learning;
- `VIABILITY` / autonomous normativity are not established;
- external memory does not establish continuous identity.

## 15. Strengthened structures

### A. Capability change triggers entrustment review, not automatic expansion

This survives child -> current AI only in corrected form:

`MATERIAL CAPABILITY CHANGE -> REASSESS CONTROL / ENTRUSTMENT / CONTAINMENT`

The direction is empirical/risk/task dependent.

### B. Safe environments can create evidence for participation

Containment/sandboxing can make it rational to allow useful initiative that would be too risky under unrestricted permissions.

This is a positive-construction mechanism:

`BOUNDARY CAN ENABLE PARTICIPATION`

The constraint is not merely a limit; it can make broader useful deployment possible.

### C. Answerable initiative survives operationally

The agent can have bounded initiative while remaining able to ask, challenge, escalate, stop and hand control back.

This is an operational collaboration target, not a standing claim.
